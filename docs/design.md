# 設計案: 地図登録の仕組み（lichens式を「みんなで登録」へ）

## lichens との違い

| 項目 | lichens | map_registry |
|---|---|---|
| 登録する人 | 自分だけ（写真アプリ→スクリプト） | 許可された複数人（ブラウザ／スマホ） |
| 公開 | 静的ファイルをGitHub Pagesへ | 地図は公開、**書き込みは認証＋承認制** |
| データ | 公開前に手元で除外検証 | 投稿ごとに承認・位置のぼかしを選べる |

## 運用モデル（推奨: 承認制）

```
登録者(許可済み) → 投稿(位置+写真+メモ) → 「保留」 → 管理者が確認 → 「公開」 → 公開地図に表示
```
- 誰でも見られる／登録者は**申請制**（決定済み）。
  - 申請フォーム（表示名・連絡先メール・利用目的）→ `applications` に保存（pending）→ 管理者が承認/却下 → 承認で `members` に追加し招待メール送信。
  - 申請の連絡先は非公開列。申請の連投・ボットは Turnstile とレート制限で抑える。
  - 投稿者の権限は段階式にできる（初期は全投稿を承認制。実績のある人は自動公開へ昇格）。
- 完全オープン登録（誰でも）はスパム・不適切画像・位置情報漏洩のリスクが大きいため**初期は採らない**。

## 構成案の比較

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. Supabase + 静的フロント（推奨）** | Postgres+PostGIS／Auth／Storage／RLS。地図はLeaflet(Vanilla JS)をGitHub Pagesに | 認証・行単位権限・画像保存が揃う。無料枠あり。既存の「Vanilla JS」方針に合う | 外部サービス依存。RLS設計ミスが最大の事故源 |
| B. GitHub Issue/PR方式 | 投稿=Issueフォーム→承認でGeoJSONに反映 | サーバー不要・履歴が残る・lichensに近い | 投稿者にGitHubアカウント必須。画像が重い |
| C. ArcGIS Online + Survey123 | Esri製をそのまま利用 | 現地入力・オフライン・グループ権限が最初からある | 有償、Esri依存、公開側の自由度が低い |
| D. Firebase | Auth+Firestore+Storage | 簡便 | 地理検索が弱い、ベンダーロック |

→ **Phase1はA**。ただし保存形式は標準（GeoJSON/CSV）で出力でき、ArcGIS（C）へも取り込める形にする。

## データモデル（案）

`points`
| 列 | 内容 |
|---|---|
| id | uuid |
| geom | PostGIS point（WGS84） |
| display_geom | 公開用の位置（ぼかし後。元位置は非公開列） |
| category | カテゴリ（例: 地衣類／被害状況／避難所…。設定で可変） |
| note | メモ（文字数制限・サニタイズ） |
| photo_path | Storage上のパス（EXIF除去後） |
| observed_at | 観察日時 |
| status | pending / approved / rejected |
| created_by | 投稿者ID（公開しない） |

## 汎用化の方針
- カテゴリ（地衣類・防災など）と各カテゴリの追加項目は `categories` テーブルの設定（JSONスキーマ）で定義し、コード変更なしに用途を足せるようにする。
- 拡張順: 汎用基盤 → 地衣類（種・同定確度など） → 防災（未確認ラベル・公的情報へのリンク必須）。

## Phase計画
- Phase0: 方針決定（本書）、規約・公開範囲の確認
- Phase1: Supabase構築、RLS、承認フロー、最小の地図＋投稿フォーム
- Phase2: 写真アップロード（EXIF除去・縮小）、位置ぼかし、`?probe=1`相当の周辺件数確認
- Phase3: 管理画面（承認／却下／通報）、GeoJSON/CSVエクスポート（ArcGIS互換）
- Phase4: 申請・招待フロー、監査ログ、バックアップ、運用手順書

## 防災用途に使う場合の注意
- 災害時は**公的情報（自治体・防災クロスビュー）が正**。本システムは補助。誤情報の拡散リスクがあるため承認制と「未確認」ラベルを必須にする。
- 被災者の氏名・住所・連絡先など**個人情報は扱わない**設計にする（扱うなら別設計・法令確認が必要）。
